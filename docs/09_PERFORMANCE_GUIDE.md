# 09. 성능 가이드

## 1. 기본 원칙

성능 최적화는 추측이 아니라 측정에 근거합니다. 초기에는 모듈형 모놀리스와 단순한 SQL 조회를 사용하고, 실제 병목이 확인된 뒤 복잡성을 추가합니다.

## 2. 성능 구간 분리

각 요청에서 다음 시간을 별도로 측정합니다.

- API 요청부터 응답 시작까지
- 질의 분류/LLM 추출 시간
- DB 조회 시간
- 암호화·복호화 시간
- 답변 생성 시간
- 첫 토큰 지연시간(TTFT)
- 전체 응답 시간

## 3. LLM

- RTX 3060 12GB 환경에서 모델 크기·양자화·컨텍스트 길이를 함께 평가합니다.
- GPU 메모리 사용량과 CPU offload 여부를 기록합니다.
- 긴 대화 전체를 매번 모델에 전달하지 않습니다.
- 요약·최근 대화·관련 기억을 조합해 필요한 문맥만 전달합니다.
- 동시 추론 수를 무리하게 늘리지 않습니다.
- 모델 다운로드 전 라이선스와 배포 조건을 확인합니다.

## 4. DB/API

- 구조화 사실은 적절한 인덱스 기반 SQL로 조회합니다.
- 페이지네이션과 상한을 적용합니다.
- N+1 조회와 불필요한 전체 조회를 방지합니다.
- 비동기 I/O 및 CancellationToken을 사용합니다.
- 쿼리 실행 계획과 실제 데이터 규모를 확인합니다.
- 암호화·복호화는 필요한 필드에만 수행합니다.

## 5. 프론트엔드

- 화면 단위로 필요한 데이터만 요청합니다.
- 긴 목록은 페이지네이션 또는 가상 스크롤을 검토합니다.
- 불필요한 상태 변경과 재렌더링을 줄입니다.
- 스트리밍 렌더링이 UI를 과도하게 갱신하지 않도록 배치합니다.

## 6. 기준선과 목표

초기에는 성능 수치를 임의로 보장하지 않습니다. 테스트 데이터 규모와 PC 사양을 기록하고 기준선을 측정합니다.

측정 시 최소한 다음을 기록합니다.

- PC CPU/RAM/GPU
- GPU VRAM 점유
- 모델명·양자화·컨텍스트
- DB 데이터 건수
- 동시 요청 수
- 평균·중앙값·p95 응답 시간
- 오류 및 타임아웃 비율

구조화된 로컬 DB 조회와 LLM 추론을 별도 지표로 관리합니다. LLM 응답이 느린 문제를 DB 최적화로 해결하려 하지 않습니다.
