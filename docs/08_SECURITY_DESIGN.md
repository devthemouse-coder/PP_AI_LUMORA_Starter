# 08. 보안 설계

## 1. 보안 목표

- 사용자 데이터 및 프롬프트의 외부 AI 서비스 전송 금지
- 저장 데이터의 기밀성·무결성 보호
- 암호화 키와 데이터의 분리
- 사용자·조직별 접근 통제
- 로그·백업·임시 파일 보호
- 오프라인 핵심 기능 보장

## 2. 암호화

민감 데이터의 애플리케이션 계층 암호화 기본 후보는 AES-256-GCM입니다.

저장 포맷은 버전 정보를 포함합니다.

- FormatVersion
- KeyId
- Nonce
- Ciphertext
- AuthenticationTag

Nonce는 키별로 재사용하지 않아야 합니다. 암호화할 때 레코드 ID·필드명 등 문맥을 AAD(Additional Authenticated Data)로 연결하는 방안을 검토합니다.

## 3. 키 관리

- 암호화 키를 DB에 저장하지 않습니다.
- DB 백업과 키 백업을 분리합니다.
- Windows 개인 설치에서는 DPAPI 등 OS 보호 기능을 키 보호 Provider 뒤에 캡슐화합니다.
- 서버/다중 사용자 환경은 서비스 계정·운영체제·키 관리 정책에 맞는 별도 Provider를 사용합니다.
- 키 생성·보관·복구·교체·폐기 절차를 문서화합니다.
- 키 분실 시 데이터 복구가 불가능할 수 있음을 사용자에게 명확히 알립니다.

## 4. 검색과 메타데이터 노출

암호문은 일반 SQL 문자열 검색이 불가능합니다. 검색용 HMAC 토큰을 사용하더라도 동일 값의 반복 여부 등 메타데이터가 노출될 수 있습니다. 검색 토큰은 별도 키를 사용하고 접근을 제한합니다.

## 5. 네트워크

- Ollama 기본 접근은 localhost/loopback으로 제한합니다.
- 외부 LLM·임베딩 API 호출 코드를 금지합니다.
- 모델 다운로드/업데이트는 승인된 별도 절차로 수행합니다.
- 오프라인 상태에서 핵심 기능을 테스트합니다.
- 방화벽·프로세스별 송신 검증으로 실제 외부 통신을 확인합니다.
- 소프트웨어 업데이트 확인 기능이 사용자 데이터를 전송하지 않도록 별도 검토합니다.

## 6. 로그

- 개인정보 원문, 대화 원문, 토큰, 비밀번호, 키를 로그에 남기지 않습니다.
- 요청 ID, 처리 시간, 오류 코드, 모델 식별자 등 최소 운영 메타데이터를 기록합니다.
- 예외 객체에 민감한 요청 본문이 포함되지 않도록 필터링합니다.

## 7. 실행 중 데이터

저장 암호화는 실행 중 메모리·GPU 메모리에 로드된 평문을 보호하지 않습니다. 로컬 OS 계정 보안, 파일 권한, 프로세스 권한, 화면 잠금, 백업 접근 권한을 함께 고려합니다.

## 8. 백업

- SQLite Online Backup API로 WAL을 포함한 일관 스냅샷을 만들고 백업 파일은 스트리밍 AES-256-GCM 형식으로 보호합니다.
- AES/HMAC 키의 DPAPI CurrentUser 보호 파일과 비밀번호 기반 키 복구 파일을 DB 백업과 분리합니다.
- 백업 복원 시 파일 인증, SQLite 무결성/FK, 스키마 버전 및 암호화 샘플을 검증합니다. 기존 DB 교체에는 명시적 승인이 필요합니다.
- 기본 보존 정책과 삭제/복원 위험은 [24–27 백업·복구 문서](24_BACKUP_STRATEGY.md)에 정의합니다.
- 백업 파일 포맷은 독립적인 보안 감사를 받지 않았으며, 운영 데이터 적용 전 검토가 필요합니다.

## 9. 개발 도구 주의

클라우드 기반 코딩 Agent에는 합성 데이터만 입력합니다. 실제 사용자 정보, DB 덤프, 비밀 설정 파일, 키 파일을 프롬프트나 첨부 파일로 제공하지 않습니다.
