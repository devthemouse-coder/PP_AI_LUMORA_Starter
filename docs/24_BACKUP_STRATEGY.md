# 24. 데이터 백업 전략

## 1. 범위와 현재 동작

현재 백업 기능은 파일 기반 SQLite와 단일 활성 AES/HMAC 키 쌍을 대상으로 합니다. SQL Server, 외부 백업 업로드, 사용자 계정 서비스, 키 회전 및 과거 키 key ring은 구현하지 않았습니다.

백업은 `Lumora.Infrastructure/Persistence/Backup/SqliteBackupService`가 수행합니다.

1. `Microsoft.Data.Sqlite.SqliteConnection.BackupDatabase`로 온라인 스냅샷을 만듭니다. 활성 DB를 파일 복사하지 않으므로 커밋된 WAL 변경도 SQLite의 백업 API를 통해 일관되게 포함됩니다.
2. 스냅샷의 `integrity_check`, `foreign_key_check`, 최신 EF Migration을 검사하고, 사용자 행이 있으면 사용자 표시명 암호문을 현재 AES 키로 복호화해 키가 맞는지 검증합니다. HMAC 토큰이 있으면 각 키 ID가 현재 검색 키와 일치하는지 검사합니다.
3. 1MiB 단위 스트리밍 AEAD 형식으로 임시 백업을 암호화합니다. 전체 DB를 메모리에 올리지 않습니다.
4. 임시 암호문을 다시 복호화하고 SQLite 검증을 한 번 더 통과한 뒤 최종 `.lumora-backup` 경로에 덮어쓰지 않고 원자적으로 이동합니다.
5. 실패하면 최종 이름의 백업을 만들지 않으며 임시 파일을 정리합니다. 프로세스 강제 종료로 남은 `.partial`, `.snapshot`, `.verify` 파일은 백업 완료 파일이 아닙니다.

SQLite 온라인 백업 호출은 SQLite Provider의 동기 API이므로 작업 전용 스레드에서 실행합니다. SQLite가 스냅샷을 만드는 동안 다른 연결의 읽기/쓰기 요청을 허용하며, 실제 WAL/동시 쓰기 통합 테스트로 확인합니다.

## 2. 암호화된 백업 파일 형식

최종 파일은 `LUMORAB1` 식별자와 형식 버전 1을 갖습니다. 인증되는 헤더에는 Backup GUID, UTC 생성 시각, 스키마 Migration ID, AES Key ID, 청크 크기(1MiB), 임의 Nonce 접두사가 있습니다. 이 메타데이터는 평문 헤더이므로 파일명·크기·생성시각·스키마 버전은 숨겨지지 않습니다.

- 활성 AES-256 키와 Backup GUID를 입력으로 HKDF-SHA-256을 적용해 백업 전용 키를 파생합니다.
- 청크별 Nonce는 임의 4바이트 접두사와 64비트 증가 순번을 결합합니다. 백업마다 GUID와 파생 키가 달라집니다.
- 각 레코드는 순번, 평문 길이, 최종 레코드 표시를 인증 데이터로 포함합니다. 전체 헤더와 바로 앞 청크의 인증 태그도 다음 청크의 AAD에 연결합니다.
- 모든 데이터 청크는 AES-256-GCM 인증 암호화되고, 파일 끝에는 빈 최종 인증 레코드가 필요합니다. 청크 재배열·중복·잘림·헤더 변조·끝에 추가된 데이터는 거부됩니다.
- 최종 백업 파일은 암호문이며, 생성 중의 임시 스냅샷/검증 DB는 Windows 현재 사용자의 임시 디렉터리에 한시적으로 존재할 수 있습니다. 강제 종료 후 남은 파일을 확인하고 제거하십시오. SSD에서 안전한 물리 삭제를 보장하지 않습니다.

이는 플랫폼의 `AesGcm`/`HKDF` 구현을 사용하는 버전 관리형 파일 형식이며 외부 암호 라이브러리를 추가하지 않습니다. 독립적인 암호 프로토콜 감사를 받은 것은 아니므로 민감한 운영 데이터에 적용하기 전 보안 검토가 필요합니다. 형식 호환성을 임의로 수정하지 말고 새 포맷 버전을 도입해야 합니다.

## 3. 키 보호 및 이전

- 원래 AES 키와 HMAC 키는 서로 다른 32바이트 난수 키이며 각각 Windows DPAPI `CurrentUser`로 보호됩니다. 키 ID도 각 키 파일에 저장됩니다.
- DPAPI 파일은 `%LOCALAPPDATA%\P.P. AI - LUMORA\keys` 또는 `Security:KeyDirectory`/`LUMORA_KEY_DIRECTORY`에 저장합니다. DB 백업 및 운영 DB와 다른 경로입니다.
- 다른 Windows 사용자나 PC에서는 DPAPI 파일을 그대로 복사해 복호화할 수 있다고 가정하지 않습니다. 키 복구 파일은 원래 두 키와 Key ID를 PBKDF2-SHA-256(600,000회, 무작위 16바이트 salt)로 만든 별도 키와 AES-256-GCM으로 보호합니다. 복구 비밀번호는 DB·설정·명령행 인수에 저장하지 않습니다.
- `.lumora-keys` 파일은 데이터베이스 백업과 다른 디렉터리 및 별도 오프라인 매체에 두고, 비밀번호는 파일과 다른 안전한 수단으로 보관합니다. 비밀번호를 잊거나 복구 파일을 잃으면 데이터를 복구할 수 없습니다.
- 새 PC/사용자에서 키 파일을 가져올 때 DPAPI 키 디렉터리가 비어 있어야 합니다. 가져오기는 기존 키 디렉터리를 덮어쓰지 않습니다.
- 키 회전, 여러 Key ID 복호화, 기존 데이터 재암호화, HMAC 토큰 재생성은 구현되지 않았습니다. 키 ID가 다르면 복원은 실패합니다. 키를 바꾸어 기존 데이터를 덮어쓰지 마십시오.

## 4. 경로, 보존 및 개인정보

- 백업 경로는 `Backup:Directory`, `LUMORA_BACKUP_DIRECTORY`, 기본 `%LOCALAPPDATA%\P.P. AI - LUMORA\backups` 순서로 결정합니다. `.lumora-backup`만 Git 제외 규칙에 포함됩니다.
- 이 설정 디렉터리 안에 새 백업을 성공적으로 만들고 재검증한 후에만 보존 정리를 실행합니다. 기본값은 최근 10개 및 90일이며, `Backup:RetentionCount`(1–1000)과 `Backup:RetentionDays`(1–3650)를 설정할 수 있습니다. 둘 중 하나라도 초과하는 오래된 백업을 정리하되 새로 검증된 최신 백업은 항상 남깁니다.
- 설정된 백업 디렉터리 밖에 명시적으로 만든 백업은 자동 정리하지 않습니다. 정상 백업 실패 시 기존 백업을 정리하지 않습니다. 키 복구 파일은 보존 정리 대상이 아닙니다.
- CLI의 백업/복원 처리에 진입한 후 성공 시각과 마지막 실패 작업·예외 형식 코드는 같은 디렉터리의 `backup-status.json`에 원자적으로 기록합니다. 실패 상태에는 파일 경로, 예외 메시지, 비밀번호 또는 데이터가 포함되지 않습니다. 상태 파일 쓰기 실패는 작업 실패로 보고되며 별도 기록 실패도 예외로 드러납니다. 이 파일은 Git에서 제외됩니다. 상태 조회용 CLI/API는 아직 제공하지 않습니다.
- `--backup`은 검증된 백업 생성 시각을 기록하고, `--restore-backup`은 별도 경로 복원 검증 시각을 기록합니다. `--replace-backup`은 기존 DB가 있었던 경우 사전 백업 시각과 복원 검증 시각을 기록합니다. 자동 주기 작업은 별도로 구현해야 합니다.
- 정기 백업은 Windows 작업 스케줄러에서 `--backup` 명령을 같은 Windows 사용자 계정으로 실행하도록 설정할 수 있습니다. 백업 명령은 외부 네트워크를 사용하지 않습니다. 작업 스케줄러 구성 자체는 생성하지 않습니다.
- DB에서 삭제한 개인정보는 이미 생성된 암호화 백업 안에 보존 기간 동안 남을 수 있습니다. 이전 백업을 복원하면 삭제된 정보가 다시 나타날 수 있습니다. 현재는 삭제 tombstone/복원 후 재적용 기능이 없으므로 삭제 요청 및 법적 보존 의무에 맞춰 백업을 폐기하거나 해당 삭제를 별도로 재적용해야 합니다.

## 5. 운영 전 점검

1. DB 백업과 키 복구 파일을 서로 다른 위치에 만들고 권한을 제한합니다.
2. 실제 운영 데이터가 아닌 합성 데이터로 다른 디렉터리 복원 절차를 연습합니다.
3. 복원된 DB의 SQLite 무결성, Migration ID, 암호화 샘플 복호화를 확인합니다.
4. 비밀번호 및 복구 파일을 분실한 경우 지원되는 우회 복구 방법이 없다는 것을 운영자에게 알립니다.
5. 정기적으로 복구 훈련을 하되 운영 DB나 운영 키를 테스트에 사용하지 않습니다.

## 6. 5단계 최종 검증 현황

| 영역 | 분류 | 확인된 동작 및 한계 |
|---|---|---|
| SQLite 온라인 백업 | 구현 및 통합 테스트 확인 | Online Backup API를 사용합니다. WAL 상태와 백업 중 쓰기 작업을 포함한 통합 테스트가 있습니다. |
| 백업 암호화 | 구현 및 통합 테스트 확인 | 청크 AES-256-GCM, 백업별 임의 식별자/nonce prefix 및 연속 순번을 사용하고 변조·잘림을 거부합니다. 자체 포맷의 독립 보안 감사는 받지 않았습니다. |
| SQLite 복원 검증 | 구현 및 통합 테스트 확인 | 별도 임시 경로에서 복호화, 무결성/FK/스키마 검증 후에만 게시합니다. 합성 DB의 사용자, Memory payload, StructuredFact를 복호화하고 HMAC 조회 토큰으로 검색되는 것을 확인합니다. |
| 암호화 샘플 확인 | 일부 구현 | 백업/복원 시 각 유형의 첫 사용자 표시명, 첫 Memory payload, 첫 StructuredFact 값만 복호화 검사합니다. 모든 암호문 행을 전수 검사한다고 보장하지 않습니다. |
| 기존 DB 교체 | 구현 및 실패 테스트 확인 | 복원본 검증과 기존 DB의 암호화 사전 백업 후 SQLite WAL Checkpoint 및 파일 교체를 시도합니다. 손상된 백업을 이용한 교체 실패에서 기존 합성 DB의 행과 무결성이 유지되는 것을 확인했습니다. 모든 Windows 파일 잠금/강제 종료 조합은 검증하지 않았습니다. |
| DPAPI 키 복구 파일 | 구현 및 현재 환경 테스트 확인 | PBKDF2-SHA-256과 AES-GCM으로 보호된 파일에서 AES/HMAC 키를 가져와 현재 테스트 Windows 사용자 DPAPI로 다시 저장하고 검증합니다. 별도 디렉터리 가져오기는 현재 Windows 계정에서 테스트했습니다. |
| 다른 Windows 사용자/PC 이전 | 코드 경로 구현, 실환경 미검증 | DPAPI 파일 자체의 타 사용자/PC 복호화는 보장하지 않습니다. 복구 파일과 비밀번호로 키를 가져오는 절차는 구현됐지만, 별도 Windows 계정이나 물리적으로 다른 PC에서 실기 검증하지 않았습니다. |
| 실패 상태와 출력 | 구현 | 백업/복원 실패 시 예외 형식 코드만 상태 파일에 기록합니다. CLI는 상세 오류/경로 대신 작업명과 예외 형식만 출력하며 비밀번호나 키를 출력하지 않습니다. 프로세스 출력을 별도로 캡처하는 자동화 테스트는 없습니다. |
| 삭제된 데이터의 백업 잔존 | 미구현 | Tombstone, 삭제 목록의 복원 후 재적용은 없습니다. 백업을 복원하면 삭제된 데이터가 다시 나타날 수 있습니다. |

이번 검증은 운영 DB를 수정하거나 백업하지 않았습니다. 별도 임시 SQLite DB와 합성 데이터로 실제 파일 백업·복원 및 복호화/검색 흐름을 테스트했습니다. 현재 작업 디렉터리의 운영 DB는 별도 읽기 전용 무결성 확인만 했으며, 그 결과를 운영 데이터의 백업·복원 성공으로 간주하지 않습니다.
