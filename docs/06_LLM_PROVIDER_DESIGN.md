# 06. LLM Provider 설계

## 1. 목적

Domain/Application이 Ollama, 특정 모델명, 공급자별 SDK·JSON 응답 구조에 종속되지 않게 합니다.

## 2. 인터페이스 방향

초기에는 다음 역할을 갖는 내부 계약을 정의합니다.

- ChatAsync: 일반 대화 요청
- StreamChatAsync: 스트리밍 대화 요청
- GetCapabilitiesAsync: 모델/Provider가 지원하는 기능 확인
- HealthCheckAsync: 연결 및 준비 상태 확인

정확한 C# 시그니처와 DTO는 구현 시 ADR로 확정합니다. Provider 전용 타입을 공통 계약에 노출하지 않습니다.

## 3. 공통 요청/응답 모델

공통 요청은 다음 항목을 표현할 수 있어야 합니다.

- 시스템 지침과 메시지 목록
- temperature 등 공통 생성 설정(지원 여부 표시)
- 응답 형식 제약(지원 여부 표시)
- 취소 토큰
- 제한 시간
- 스트리밍 여부

응답은 텍스트, 종료 상태, 사용 가능한 경우 토큰 사용량, 모델 식별 정보, 오류 분류를 포함합니다.

## 4. 기능 차이

모든 모델이 JSON 모드, Tool Calling, Vision, 긴 컨텍스트를 지원한다고 가정하지 않습니다.

Provider는 capability를 보고하고 Application은 기능 지원 여부를 확인합니다. 미지원 기능은 명확한 오류 또는 대체 절차를 사용합니다.

## 5. 오류 분류

- 연결 불가
- 모델 미설치
- 모델 로딩 실패
- 요청 시간 초과
- 사용자 취소
- 메모리 부족
- 지원하지 않는 기능
- 응답 형식 검증 실패

오류 메시지에 프롬프트 원문이나 개인정보를 포함하지 않습니다.

## 6. Ollama 초기 구현

- 기본 주소는 로컬 루프백으로 제한합니다.
- 사용자 데이터가 외부 endpoint로 전달되지 않도록 합니다.
- 모델 다운로드는 별도 사용자 승인 작업으로 취급합니다.
- 모델 태그·양자화·라이선스·다운로드 날짜·테스트 결과를 기록합니다.
- Ollama API의 응답 구조는 Ollama Provider 내부에서만 변환합니다.

## 7. 모델 교체 테스트

새 Provider를 추가할 때 동일한 계약 테스트를 수행합니다.

- 한국어 일반 질문
- 긴 입력 처리
- 취소 및 시간 초과
- 스트리밍 종료
- JSON 추출 결과 검증
- 미지원 기능 처리
- 잘못된 응답 처리
- 네트워크 외부 송신 여부

## 8. 금지 사항

- Application에서 Ollama HTTP API를 직접 호출하지 않습니다.
- Domain에 모델명이나 Ollama 전용 옵션을 저장하지 않습니다.
- 특정 모델의 출력 문구를 정답으로 하드코딩하지 않습니다.
- 모델의 자연어 답변을 사실 데이터의 근거로 간주하지 않습니다.
