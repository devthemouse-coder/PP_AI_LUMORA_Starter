# ADR-0005: SQLite 백업 및 키 복구 파일

- 상태: 채택
- 날짜: 2026-11-08

## 맥락

SQLite는 WAL 동작 중 DB 파일만 복사하면 일관된 스냅샷이 보장되지 않습니다. 사용자 필드는 AES-GCM으로 암호화되지만 DB 파일 백업 자체와 DPAPI `CurrentUser` 키 파일은 서로 다른 장애/이전 시나리오를 갖습니다. DPAPI만으로 다른 Windows 사용자나 PC에서 키를 복구할 수 없습니다.

## 결정

1. SQLite `BackupDatabase` 온라인 API로 파일 기반 스냅샷을 만듭니다.
2. 전체 파일을 메모리에 넣지 않는 버전 관리형 청크 AES-256-GCM 백업 컨테이너를 사용합니다. HKDF-SHA-256으로 백업마다 키를 파생하며 헤더·순번·이전 태그를 인증해 재배열/잘림을 거부합니다.
3. AES/HMAC 원키는 분리된 DPAPI CurrentUser 파일에 유지하고, 다른 환경을 위한 별도 `.lumora-keys` 파일은 사용자 비밀번호 기반 PBKDF2-SHA-256(600,000회) 및 AES-256-GCM으로 보호합니다.
4. 복원은 새 임시 SQLite 파일에서 인증·무결성·FK·스키마·키 샘플 복호화를 확인합니다. 기존 DB 교체는 명시적 승인, 사전 암호화 백업, WAL Checkpoint 및 원자 교체가 모두 준비된 경우에만 시도합니다.
5. 보존 기본값은 최근 10개/90일로 하되, 설정된 백업 디렉터리에서 새 백업을 검증한 다음에만 오래된 백업 정리를 수행합니다. 최신 검증 백업과 키 복구 파일을 자동 삭제하지 않습니다.

## 검토한 대안

- DB 파일 단순 복사: WAL의 일관성을 보장하지 않으므로 거부.
- DB와 DPAPI 파일을 하나의 백업에 함께 보관: DPAPI의 환경 결합 및 키/데이터 분리 원칙을 훼손하므로 거부.
- 외부 백업 서비스/클라우드 KMS: 사용자 데이터의 네트워크 전송 금지 및 현 단계 오프라인 원칙 때문에 거부.
- 추가 암호화 패키지: 현재 요구에 맞는 검증/라이선스/배포 조건을 확인하지 않고 추가하지 않음. 프레임워크 `AesGcm`, `HKDF`, `Rfc2898DeriveBytes`를 사용.

## 결과 및 미결정 위험

- 백업 스트리밍 포맷을 직접 정의하므로 독립 보안 검토가 필요하며, 형식은 버전 변경 없이 수정하지 않습니다.
- 별도 PC 이전은 암호화 키 복구 파일로 설계되었으나 실제 별도 장치 실기 검증은 수행하지 않았습니다.
- 키 회전/key ring, 삭제 tombstone, 자동 스케줄러, 백업 파일 서명, SQL Server 전략은 미구현입니다.
- 복원 후 SQLite DB는 DB와 사용자 키가 분리된 로컬 파일입니다. 디스크 전체 암호화, ACL 및 오프라인 매체 권한 관리는 운영자 책임입니다.

## 후속 조치

- 민감한 운영 데이터를 적재하기 전에 보안 담당자가 백업 포맷/nonce/AAD/잘림 방지 구현을 독립 검토합니다.
- 다른 Windows PC 및 계정에서 합성 키/DB로 이전 리허설을 수행합니다.
- 삭제 요구가 있는 제품 단계에서 tombstone/백업 만료와 복원 후 삭제 재적용 정책을 설계합니다.
