# 27. 데이터 및 백업 보존 정책

## 1. 기본 보존 정책

백업은 성공적으로 생성하고 재검증한 경우에만 보존 정리를 수행합니다. `Backup:Directory` 또는 `LUMORA_BACKUP_DIRECTORY`에 생성된 `*.lumora-backup`만 대상이며 기본 정책은 최근 10개와 90일입니다.

```json
{
  "Backup": {
    "Directory": "",
    "RetentionCount": 10,
    "RetentionDays": 90
  }
}
```

- `RetentionCount`: 1–1000. 기본 10개
- `RetentionDays`: 1–3650. 기본 90일
- 개수와 기간 중 하나라도 벗어난 과거 백업은 새로운 백업 생성·암호화·내부 복호화 및 SQLite 검증이 성공한 다음에만 정리할 수 있습니다.
- 새로 검증된 최신 백업은 항상 남겨 적어도 하나의 방금 검증된 백업을 보존합니다. 백업 생성 실패 시 기존 파일을 정리하지 않습니다.
- 설정된 백업 경로 밖에서 만든 `.lumora-backup`은 자동으로 정리하지 않습니다. 키 복구 파일은 자동 삭제하지 않습니다.
- 자동 주기 작업은 제공하지 않습니다. Windows 작업 스케줄러는 운영자가 별도 설정하고, 작업이 같은 Windows 계정/DPAPI 사용자로 실행되는지 확인해야 합니다.

## 2. 삭제와 과거 백업

현재 삭제 기능이 운영 API로 노출되지는 않았습니다. 향후 사용자/테넌트 삭제 기능을 구현할 때 운영 DB에서 사용자 소유 데이터, 암호화 본문, revisions, lookup tokens를 함께 삭제해야 합니다. 백업은 immutable snapshot이므로 원본 DB의 삭제가 과거 백업 파일을 소급 변경하지 않습니다.

- 삭제 요청 처리 시 관련 백업의 생성 시점과 최대 보존 기간을 확인합니다.
- 만료된 백업의 삭제는 별도 승인된 운영 절차로 수행합니다. 삭제된 백업은 복구할 수 없습니다.
- 법적 보존 의무와 개인정보 삭제 요청은 관할 정책에 따라 조정해야 하며, 임의로 영구 보존을 택하지 않습니다.
- 키 복구 파일에는 DB 외부의 복구 키가 암호화되어 있으므로 키 파일 분실/폐기 정책을 DB 백업과 따로 관리합니다. 운영 데이터 복구에 필요한 키를 DB 백업과 함께 자동 삭제하지 않습니다.

## 3. 복원 후 삭제된 정보 재등장

이 버전에는 삭제 tombstone, 백업 무효화 목록, 복원 후 삭제 이력 재적용 기능이 없습니다. 따라서 삭제 시점 이전 백업을 복원하면 이미 삭제된 사용자 데이터가 다시 나타날 수 있습니다.

복원 전에 삭제 요청/보존 기록을 검토하고, 복원 후 필요한 삭제를 다시 적용해야 합니다. 이 기능이 필요한 운영 환경에서는 tombstone의 별도 보호·동기화·만료 규칙을 설계한 후 구현해야 합니다. 백업이 존재한다는 이유로 삭제 정보를 무기한 유지하거나 자동 재등장시키는 동작을 안전하다고 간주하지 마십시오.

## 4. 보존 정리 실패

새로 검증된 최신 백업은 보존 정리 중 예외가 나더라도 우선 생성되어 남습니다. 정리 실패는 명령에서 오류로 보고될 수 있습니다. 백업 디렉터리 용량, ACL 및 사용 중 파일을 확인하고, 수동 삭제 전에 다른 복구 가능한 암호화 백업과 키 복구 파일이 있는지 별도로 검증하십시오.

## 5. 검증 범위

기본 10개/90일 정책과 성공적으로 검증한 새 백업 후의 보존 정리는 SQLite 임시 DB 통합 테스트로 확인했습니다. 운영자는 별도로 백업 디렉터리의 ACL, 저장장치 여유 공간, 키 복구 파일의 접근 통제 및 실제 보존 의무를 관리해야 합니다. 보존 기간이 지난 시점의 자동 백업 삭제나 삭제 이력의 복원 후 재적용은 구현되어 있지 않습니다. 백업 파일 삭제는 되돌릴 수 없으므로 복구에 필요한 백업과 키가 남는지 확인한 후 수동으로 수행하십시오.
